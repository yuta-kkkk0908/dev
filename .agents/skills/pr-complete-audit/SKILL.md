# PR Complete Audit

目的は、**レビュー初回で発見可能な問題を一括で提示すること**。指摘を逐次投稿し、修正後に別の見落としを繰り返す運用を避ける。完全性は根拠付きの調査範囲で示し、調べられなかった範囲を推測で合格にしない。

## 0. 実行境界

- ユーザーの指定したリポジトリ・PR・対象ブランチだけを扱う。対象PRが不明なら、現在の会話・チェックアウト・Issueリンクから特定する。
- **監査は原則読み取り専用**。コード修正、コミット、PRへのレビュー投稿、Issue更新、CI再実行、マージなどは、それぞれユーザーの指示または既存の明示的な委任がある場合だけ行う。「レビューして」は監査結果の提示を意味し、投稿・マージを自動で含めない。
- 新規worktreeは作らず、既存のworktree・ブランチを勝手に切り替えない。必要な Git 操作は原則 read-only に限定する。
- リポジトリの `AGENTS.md`、関連設計・Issue・受入基準と矛盾しない。Issue 化済みなら要件/基本設計は決定済みとして扱い、設計品質の穴埋めをユーザーに依頼しない。**未承認の仕様判断**だけを明示する。
- リポジトリ外・関連しない既存欠陥は、本PRが導入/顕在化/悪化させたものでなければ指摘対象外。必要なら「既存問題・別件」と分離。

## 1. PRスナップショットを確定する

レビュー対象を `repository`, `PR#`, `base ref/SHA`, `head ref/SHA`, `merge-base`, `取得時刻` で固定し、以後の証跡に紐付ける。可能なら `gh pr view`, `gh api --paginate`, `git diff`, CI/Actions 情報を使う。GitHub コネクタでも同じ情報を収集する。**ツールに応じて代替可能**であり、コマンド実行自体を目的にしない。

最低限集めるもの：

1. PRの本文、目的、リンクされた Issue、採用済み設計、対象 base/head、未解決レビューコメント、マージ可否・競合。
2. **全ページ**の changed files 一覧（追加/削除/改名/生成物を含む）、変更統計、各ファイルの patch または前後の実体。差分が省略/切断されたファイルは個別取得する。
3. CI・チェック・テスト結果と実行 SHA。失敗した job のログ。人間確認を要するUI/映像/Unity実機等の証跡有無。
4. モノレポ/複数環境なら関連ビルド・設定・データ・移行・依存パッケージの版差。

**全ファイルを列挙できない・主要ファイルが読めない・対象SHAが不定の場合、監査を完了と表示しない**。調査可能な範囲を提示し、未検証項目を明記する。レビュー途中で head が変わった場合は新SHAとの差分を取り直す。

## 2. 差分だけを見て終わらない

全変更ファイルに対し変更意図を割り当て、`references/coverage-matrix.md` の調査軸を適用する。少なくとも以下の一連の流れを追う。

1. **仕様と責務**：Issueの受入条件・不変条件・既存API契約に対して、実装の抜け/余計な変更/スコープ逸脱はないか。
2. **双方向の参照**：変更された公開型・関数・イベント・DTO・状態遷移の**呼び出し元／利用者／依存先**を検索する。型の適合だけでなく値・意味・タイミングを確認。削除・改名の参照漏れも調べる。
3. **動作経路**：正常・異常・境界・取消・再試行・並列・復旧・再入・部分成功・null/空値・旧データと互換性・Feature flag/設定違いを、関係する経路で検証。
4. **統合と回帰**：UI→API→永続化→Worker/外部依存→表示、またはゲーム状態→セーブ→復帰のように、実際の入口から出口まで接続を追う。変更されない周辺機能の回帰条件も調べる。
5. **テストの妥当性**：テスト件数ではなく、変更契約への対応・失敗すべきケース・assertionの強さ・実行環境・SHA一致を確かめる。必要に応じて既存テストを実行。 `PASS`、`FAIL`、`NOT RUN`、`NOT AVAILABLE` を明確に区別。
6. **運用/安全**：認証認可、秘密情報、ファイルI/O、エラーハンドリング、破壊的変更、DB migration、バックフィル、リソース/タイムアウト、ライセンス・配布条件等を関連がある場合に確認。

探索範囲は**変更の影響経路**で有界にする。関係ない全リポジトリを無条件に精査しない。ただし追跡して初めて見つかる関連呼び出しは対象に含める。

## 3. 証拠と検証レベル

- 指摘はすべて `根拠位置（path:line またはURL） / 発火条件 / 現象と影響 / 原因 / 修正方針 / 必要な再検証` で具体化する。推測なら推測と明記し、再現未確認の深刻度は証拠に見合うよう設定。
- 差分行だけで説明しきれない場合、呼び出し元・既存契約等の証拠も示す。該当コードを確認していない一般論は「欠陥」として列挙しない。
- テスト証跡は `自分で実行してPASS` / `CIログで同一SHAのPASSを確認` / `PR本文の申告のみ` / `未実施` を区別。マージ後のQAは、PRブランチのテストで代替しない。
- 大規模変更は**ファイル単位の調査状況表**で抜けを可視化し、調査後に最終レビューを一度だけまとめる。読み切れない場合は `INCOMPLETE` で終了し、未監査なのに「問題なし」としない。

## 4. 最初の発信前に統合・自己点検する

初回の**レビュー指摘を公開する前**に、以下の順に内部で確定する。

1. 変更ファイル全件の監査状況と、重要経路の呼び出し元・依存先の確認状況を棚卸し。
2. すべての懸念を重大度順に収集し、重複・派生症状は根本原因単位に統合。
3. 各指摘の再現条件・根拠が正しいか反証を試す。仕様上正しい挙動を誤検知しない。
4. 重大度・ユーザーが判断すべき仕様事項・テスト不足を切り分ける。
5. head SHA を再照合し、変更されていたら差分追加分と影響先を再監査。
6. **その時点で確認できた指摘を一度に全部提示**。小出しのコメントを作らない。

初回公開後の追記は、修正による新規コード、取得不能だった追加証跡、または見落としの明示的訂正がある場合のみ。新発見を隠さず、**なぜ初回に検出できなかったか**と再発防止のチェック漏れを記録する。

## 5. 判定と出力

監査結果のフォーマットは `references/review-report.md` に従う。重大度を `P0 即時停止`、`P1 マージ阻止`、`P2 要修正`、`P3 軽微` とし、指摘は重大度の高い順に集約する。

- `READY`: 既知のP0/P1/P2がなく、重要な検証経路が確認され、必要なCI・受入条件が満たされている。
- `CHANGES_REQUIRED`: 修正すべきP0/P1/P2が存在する。**具体的な修正・テスト条件をすべて一括提示**する。
- `INCOMPLETE`: 重要な変更ファイル・依存先・CI・実機受入などの証拠不足により判断不能。欠陥がないことを意味しない。

初回レビューには「確認済み範囲」「未確認範囲」「テスト証拠の種類」「マージ判断」「全指摘」「修正後の一括再検証計画」を必ず含める。未指摘の問題が将来存在しないとの保証はしない。

## 6. GitHubへの投稿・マージが指示された場合だけ

- 監査完了後、独立した投稿操作を行う。既存コメント・未解決スレッドと重複しないようまとめる。PRレビュー投稿では、ユーザーに必要な一括指摘を可能な限り単一のレビュー本文へ集約する。
- PR作者・実行アカウントを確認する。**自分が作者のPRに `REQUEST_CHANGES` を試行しない**。その場合は `COMMENT`（許可されている場合）または通常コメントで欠陥・ブロッカーを記録する。`APPROVE` が許可されない自己承認も試みない。
- コメント投稿が許可されても修正・mergeが許可されたことにはならない。**マージは明示指示がある時だけ**。必要なCI/QA/受入条件が欠ける場合はマージせず理由を示す。
- マージを実行した場合は実際の merged 状態・統合SHA・Issueステータス・post-merge QA残件を再取得し、**Feature PR merged と Gate/QA completed を区別**して報告する。

## 7. 修正確認時

指摘への対応を個別に確認するだけで終わらない。前回レビューの SHA→現 SHAの増分差分をすべて読み、新規変更と旧契約の回帰をまとめて再監査。解消表は `FIXED / STILL OPEN / REGRESSED / NOT VERIFIED` を使用し、修正前の問題と新規欠陥を統合した**一度の再レビュー**で伝える。
